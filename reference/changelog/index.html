    Changelog¶

    All notable changes to Forge are documented here. Format follows Keep a Changelog. Versioning follows Semantic Versioning.

    [Unreleased]¶

    Added¶

    • ToolConnector adapter and forge tools inventory (last 4b checkpoint).
    • forge.tools.mcp.adapter.mount() puts a proprietary connector (backend, describe(), call()) behind an in-process MCP server. Its tools then get the same hashing, approval and handling as any MCP tool.
    • forge tools inventory writes tool-inventory.v1 for the suite's tool_connectors vector. It lists every approved tool, and skipped tools are listed on stderr.
    • Every row carries backend. It comes from mcp-servers.toml, where each server must declare backend ("self-contained" or the service it depends on), with optional per-tool tool_backends overrides. An adapter takes it from the connector.
    • An adapter tool is never written with backend: null. mount refuses a connector without a real backend, and the writer refuses again.
    • The inventory is checked against the suite's rules before it is written.
    • A contract test feeds the writer's output to the suite's reader and scoring.
    • MCP policy requests match AgentPolicyPack's request model.
    • mcp.server.connect carries resource: {id, type: McpServer, attributes: {transport, origin, hosting}}.
    • tool.call carries resource: {id: <server>/<tool>, type: McpTool, attributes}, the tool block, and the arguments under context.
    • A bundle can therefore target hosted servers or one server's tools with no AgentPolicyPack change. See its examples/mcp_governance/.
    • forge mcp serve / McpToolServer: Forge tools as an MCP server (checkpoint 9b). The owner's exposure rules are enforced before anything listens:
    • off by default;
    • only tools named with --expose, never "all";
    • dangerous tools (http_get, sandboxed execution) need --allow-dangerous as well;
    • stdio by default, and HTTP on loopback only unless --allow-non-loopback;
    • HTTP requires a bearer token (from an environment variable) or an OAuth token_verifier. OAuth tokens must be issued for this server's resource (RFC 8707).

    Every inbound call is audited, including refused and unauthenticated ones, as agentforge.mcp.server_call: caller, tool, outcome and duration, with redacted, capped arguments, any injection indicators, and the result's digest and length (never its content).

    Caller input is treated as untrusted: bounded, cleaned, schema-validated, screened, and run under the sandbox policy and timeout. Failures reach the caller as their exception class only. - Contract tests for tool-inventory.v1. Ahead of forge tools inventory, a contract module pins three things against the suite: - the names, origins and definition hashes a connector records fit the suite's inventory reader; - backend is required on every tool; - a tool with a vendor-only backend scores 75 or 100, never 25, even when approved and local. - suite-contract covers the MCP formats. tool-approvals.v1, mcp-servers.v1 and tool-definition.v1 are now owned by the AI Infrastructure Suite. A new contract module checks four things: - the copies packaged here have not drifted from the suite's; - every approvals file and definition snapshot Forge writes meets the suite's schemas, and approvals also parse with the suite's stricter reader; - every server origin Forge records is one the suite accepts; - both sides refuse the same invalid server entries. - forge mcp status and forge mcp approve. Approving an MCP tool always shows what is being approved: - a new tool's full definition (description, input and output schema, annotations); - for a changed tool, a field-by-field diff against the approved definition, plus any change of server origin; - the screening reasons for any flag, taken from the whole description and from the schemas.

    The rules: - A flagged tool needs --accept-flagged. - A changed or flagged tool is confirmed by typing its name, never by y/n. Without a prompt (--yes) it needs --expect-sha256 with the offered hash. - --all-new covers only new, unflagged tools, and lists the rest for individual review. - Each approval is audited as agentforge.mcp.tool_approval with the new and previous hashes.

    Server text is printed with control and bidirectional characters escaped, and never through a markup renderer. forge mcp loads the MCP package only when it runs, and says how to install the extra when the SDK is missing. - mcp-servers.v1 (mcp-servers.toml): the servers Forge may contact, with paths to the approvals file and snapshot directory relative to it. It has a JSON Schema and a fixture. It is a separate file because core configuration never imports the MCP package. - tool-definition.v1 snapshots (tool-definitions/<sha256>.json, beside tool-approvals.json). They hold the approved definition so a later change can be shown as a diff. Each is self-verifying, so an edited snapshot is refused. It has a JSON Schema and a fixture. - DiscoveredTool.raw_description and DiscoveredTool.definition(). - A source-hygiene test: no file in forge/, tests/, docs/ or examples/ may contain bidirectional-control or escape characters.

    • MCP tool connectors (Phase 4b, client side). Install agentforge-oss[mcp], which adds the optional extra mcp>=2.3,<3 (MIT). Core AgentForge never imports mcp, and a test enforces it both statically and in a fresh interpreter.
    • forge.tools.mcp.McpConnector connects to one configured server over Streamable HTTP, stdio or in-process, using the 2026-07-28 protocol (server/discover). It refuses a server that offers only the older initialize handshake.
    • It lists and hashes every tool and offers only approved ones, as McpTool (dangerous=True, named <server_id>__<tool>). refresh() re-hashes and watch() follows subscriptions/listen; neither ever approves anything.
    • Rug-pull defense.
    • The definition hash is SHA-256 over the RFC 8785 canonical JSON of {server_id, name, description, inputSchema, outputSchema, annotations}. The canonical JSON is a standard-library implementation, checked against the RFC's examples.
    • Approvals are kept in a new tool-approvals.v1 file, with a JSON Schema (forge/tools/mcp/tool-approvals.schema.json), a strict bounded reader, and fixtures in docs/examples/mcp/.
    • Each tool is classified as approved, pending, changed, returned or invalid. Only approved tools are offered.
    • A changed definition is refused and emits mcp.tool.definition_changed with both hashes and never the description. The same record is audited as agentforge.mcp.tool_definition_changed.
    • connector.approve() screens the description and schema first. A flagged definition needs accept_flagged=True, and the accepted reasons are kept in the approval.
    • Untrusted content.
    • Descriptions are capped at 1 KiB, with control and bidirectional-override characters stripped.
    • Schemas are bounded: 64 KiB, depth 16, 128 properties, no remote $ref, no $id.
    • Arguments are validated against the approved schema before sending.
    • Results are stripped, capped, screened (mcp.result.flagged) and framed as untrusted data.
    • A server's error text never reaches a prompt, event, log or audit record; only the error class does.
    • Three SDK behaviours are turned off:
      • the client cache;
      • the automatic re-list-and-resend on HEADER_MISMATCH, which now re-hashes and refuses instead;
      • every server-to-client feature (sampling, roots, elicitation, logging).
    • Policy hooks. connect_policy and call_policy receive AgentPolicyPack-shaped mcp.server.connect and tool.call requests. The tool.call request carries tool.namespace = "mcp.<server_id>" and tool.definition_sha256. A denied connect never contacts the server.
    • OAuth: forge.tools.mcp.ForgeOAuthProvider is the SDK provider (RFC 9728, RFC 8707, PKCE) with three Forge rules:
    • iss is always required on the authorization response, and is refused before the code is redeemed if missing.
    • Client ID Metadata Documents only: no fallback to dynamic client registration, no registration request ever sent, and a stored non-CIMD registration is refused.
    • The SDK's trailing-slash equivalence for root issuers in metadata is documented.
    • McpServerConfig applies the endpoint URL rule (no credentials, query or fragment; default_query redacted), records the origin only, and derives hosting from it. stdio servers get an environment allowlist, and bearer tokens are referenced by environment variable name.
    • New events mcp.server.connected, mcp.server.refused, mcp.tool.refused, mcp.tool.definition_changed and mcp.result.flagged. New exceptions McpError (a ToolError) and McpAuthError. New guide docs/guides/mcp.md.
    • ToolResult.untrusted (default False) and Tool.untrusted_results (default False): the sandbox marks results from untrusted tools, such as MCP tools. Both are additive.

    Changed¶

    • McpConnector.screen() now screens the full description, the output schema and the annotations, not only the capped description and the input schema.
    • The connector takes http_transport= (custom TLS, a proxy, or an in-process app in tests).

    Fixed¶

    • CLI error messages print as plain text. forge run, forge providers inventory, forge memory migrate and every command that fails through the shared _fail helper interpolated the error message into a Rich markup string. Text in square brackets was therefore read as markup:
    • swallowed (agentforge-oss[sqlite] printed as agentforge-oss);
    • restyled;
    • or, for an unmatched closing tag, turned into a MarkupError instead of the error.

    Affects every published version through 0.5.9. Messages are now printed verbatim; only the Error: label is styled. - ToolRegistry.register no longer replaces a same-named tool silently. Affects every published version through 0.5.9. Registering a second tool under a name already in use swapped it in without any signal, so whatever an agent ran under that name could change unseen (an in-process rug pull). It now raises the new DuplicateToolError (a ToolError, exported from forge). The same applies to ToolRegistry(...) and extend(...). Replacement must be explicit: register(tool, replace=True) or extend(tools, replace=True). Registering the very same tool object again is a no-op. Migration: code that relied on re-registering a name to override a tool must pass replace=True.

    [0.5.9] - 2026-11-25¶

    Portable memory (Phase 4a). The bundled memory stores can now be exported as agent-memory.v1, imported back with every item quarantined until reviewed, and migrated in place. Exports this version writes are scored by AI Infrastructure Suite 0.2.0b3 or later (memory_inventory); Memory itself is unchanged, so third-party backends keep working. Opening an existing SQLite or pgvector store applies an additive migration (see Changed); run forge memory migrate --print-sql first if a DBA must apply it.

    Added¶

    • PortableMemory (forge.memory.portable), an optional interface the three bundled backends now implement: list_records (paged by ID), list_tombstones, import_records, delete_record, review_records and embedding_scheme. Memory itself is unchanged (add / search / clear), so third-party backends keep working; one that does not implement the new interface is simply not exportable. Phase 4a, checkpoint 3.
    • Imported memory is untrusted. Imports keep their IDs and land quarantined: listed, but never returned by search until a reviewer activates them. Re-importing an identical item is a no-op; the same ID with different content is refused, never overwritten; an import carrying reserved _forge_* metadata is refused; a record cannot set its own status or provenance. Provenance (source system, export digest, original ID, import time, importer) is stored apart from user metadata.
    • Deletions stick. delete_record removes an item and leaves a tombstone holding only its ID and time; an import never resurrects a tombstoned ID, and an item a reviewer rejected is never imported again. Tombstones survive clear().

    • forge memory migrate applies the configured store's schema migration deliberately; --print-sql prints the statements instead, for a DBA to apply, and opens no connection. Opening a store runs the same migration automatically. A migration that fails, for example because the database user lacks ALTER or CREATE privileges, raises the new MemoryMigrationError (a MemoryBackendError) saying what to run; it never surfaces a raw database error, and its pool is closed.

    • Memory export and import (forge.memory.transfer, Phase 4a checkpoint 4). export_memory writes a portable store as agent-memory.v1 into an empty directory: items in digested JSONL shards, tombstones as an ID and a time, and the vectors in a linked embedding-portability.v1 whose records are the items, recomputed over exactly the exported text so each vector is bound to its item by content_sha256. Bytes are canonical, so the same store exports identically. export_conversation writes a conversation transcript (messages numbered msg-000000, ...). import_memory re-checks every digest, applies the export's tombstones first, imports items as quarantined, and writes an agent-memory-import.v1 report bound to the export's digest. The AI Infrastructure Suite scores such an export at 25 for the memory vector.

    • No secrets leave. An export stops, writing nothing, if any item's text or metadata still looks like a credential (private keys, cloud access-key IDs, common API-token formats, JWTs, bearer headers, URLs with credentials); the error names the item and the kind, never the value, and lists the ways to proceed. There is no option to export the credential itself:
    • redact_secrets=True (--redact-secrets) replaces each detected credential with [REDACTED:<kind>] and records the redaction profile in the document (secrets, or pii-and-secrets with redact_pii);
    • exclude={item_id: reason} (--exclude ITEM --exclude-reason "...") leaves named items out of this export; the reason is required, each exclusion is recorded in the audit log as agentforge.memory.export_exclusion with the operator and the export digest, and the item is not deleted;
    • or delete the item under policy, which leaves a tombstone. redact_pii=True applies the PII redactor first and records it too.
    • Review before use. forge.memory.review.list_quarantine shows quarantined items with their source and any prompt-injection indicators, never their text. review_items activates or rejects them by ID or by export; a flagged item is activated only on its own with accept_flagged=True, and bulk activation skips flagged items. Decisions can be recorded in the audit log as agentforge.memory.review.
    • Memory is never a system prompt. forge.memory.context.memory_context_message renders retrieved memory as a quoted, labelled, untrusted block in a user message; a test scans the package so that no function both searches memory and builds a system message.
    • CLI: forge memory export, forge memory import (audited as agentforge.memory.import), forge memory quarantine, forge memory review.
    • The suite-contract job now also checks every memory export variant, the conversation export and the import report against the suite's schemas and readers, including a memory_inventory score of 25.

    Changed¶

    • Additive schema migrations, run when a store opens or by forge memory migrate. Every statement is idempotent; nothing is dropped, renamed or rewritten, and existing rows read back as active and native.
    • pgvector, on the existing table (default forge_memories; shown as <table>):
      • column item_id TEXT (nullable): the original ID of an imported row;
      • column status TEXT NOT NULL DEFAULT 'active';
      • column provenance JSONB (nullable);
      • unique index <table>_item_id_idx on (COALESCE(item_id, id::text)), built CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS, so the IDs add and search return are unchanged;
      • new tables <table>_tombstones and <table>_rejected. Locks: each ADD COLUMN (NULL or constant default) is a catalog-only change holding an ACCESS EXCLUSIVE lock briefly; the index builds concurrently, so writes continue. An index left invalid by an interrupted concurrent build is detected and reported (drop it and re-run), never silently skipped. A dimension mismatch is refused before any schema change.
    • SQLite, on the existing memories table: columns status TEXT NOT NULL DEFAULT 'active' and provenance TEXT, each added only when missing; new tables memory_tombstones, memory_rejected and forge_memory_meta. The meta table records the store's scheme and dimension, so even an empty store refuses to reopen at another dimension.

    [0.5.8] - 2026-11-25¶

    A bug-fix release. Memory search no longer returns wrong rankings when a store's vectors and its configured dimension differ: it raises MemoryDimensionError instead. The pgvector examples and the missing-DSN error also stop showing a database password inside the DSN (use PGPASSWORD or a .pgpass file). No API is removed or changed.

    Fixed¶

    • Memory search no longer compares vectors of different dimensions. SQLiteMemoryStore.search paired the query vector with each stored vector using zip(..., strict=False), so a store built at one embedding_dim and opened at another (the in-memory store defaults to 512, SQLite and pgvector to 64) truncated the longer vector and returned wrong rankings with no error. Affects SQLiteMemoryStore in every release from 0.3.0 through 0.5.7. It now raises the new MemoryDimensionError (a MemoryBackendError) when the store opens, before a vector of a second dimension can be written, and again in search for a table that already holds two. PGVectorMemoryStore (0.5.1 through 0.5.7) was not silent, since PostgreSQL refused the query, but failed on every call with a database error; it now checks the table's declared dimension on open and raises the same clear error. The in-memory store builds every vector itself and compares strictly, so it was not affected. The error names both dimensions and never repeats stored text.

    [0.5.7] - 2026-11-25¶

    Adds forge providers inventory, which writes the provider-inventory.v1 evidence the AI Infrastructure Suite's model_providers vector reads, and stops treating documentation, benchmarking, reserved and broadcast addresses as local. Inventories that mark registry models or an SDK endpoint override need AI Infrastructure Suite 0.2.0b2 or later; an inventory without either marker is also readable by 0.2.0b1. No breaking change: the new command is additive and every existing API is unchanged.

    Added¶

    • forge providers inventory writes a provider-inventory.v1 document for the configured providers, for the AI Infrastructure Suite's model_providers lock-in vector. Endpoint origins only (scheme, host, port); hosting is left for the suite to derive; jurisdiction is a preset's stated value or unknown. Features in use, vendor-only features and their reconstruction paths are never guessed: they come from a new provider-declarations.v1 file (schema in forge/models/data/provider-declarations.schema.json), and a configured provider without a declaration is refused. Models in use are declared too: a provider without them is refused unless --use-registry-models is passed, and then its registry models are marked "source": "registry" (from registry, not confirmed in use). An openai or anthropic provider at its SDK default is marked "endpoint_override_present": true when OPENAI_BASE_URL or ANTHROPIC_BASE_URL is set: present, not reflected, and the variable's value is never written. An inventory that uses either marker needs AI Infrastructure Suite 0.2.0b2 or later; one that uses neither is also readable by 0.2.0b1. See the providers guide.
    • Orchestrator.configured_providers(config) returns the providers a default run would build, without building the rest of the orchestrator.
    • A suite-contract CI job installs the suite from its main branch and checks every inventory the command can write against the suite's schema and reader, and this package's locality rule against the shared table.

    Fixed¶

    • Reserved and limited-broadcast addresses are hosted, not local. 240.0.0.0/4 (RFC 1112 reserved) and 255.255.255.255, and their IPv4-mapped forms. Python's is_private includes them, so endpoint_is_local and hosting_for called an endpoint there local. Pinned by six new cases in the shared endpoint-locality-cases.v1 table.
    • The documentation and benchmarking ranges are hosted, not local. 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24, 198.18.0.0/15 and 2001:db8::/32, and their IPv4-mapped forms. Python's is_private includes them, so endpoint_is_local and hosting_for called an endpoint there local, and events reported its hosting as local. Pinned by the AI Infrastructure Suite's shared endpoint-locality-cases.v1 table, vendored in tests/fixtures/.

    [0.5.6] - 2026-11-24¶

    A security release that closes what 0.5.5 left open. If you have a token in any URL's query string, move it: such a URL is now refused, and the token was being logged. Two behaviours change on purpose, both under Changed: OllamaProvider refuses credentials in its URL instead of sending them as a header, and failure events and audit records now carry the exception type and a fixed description instead of the exception's own text.

    Security¶

    • A token in a URL's query string was accepted and logged. Affects 0.5.5 and earlier. 0.5.5 refused credentials in a base_url but accepted https://host/v1?key=..., and the HTTP client logs the full request URL at INFO, so the token reached any log that captured INFO output. Every configured URL now follows one rule: credentials, fragments and query strings are refused, for the provider base URLs, the OPENAI_BASE_URL, ANTHROPIC_BASE_URL and OLLAMA_BASE_URL variables the SDKs read themselves (ANTHROPIC_BASE_URL was not checked before), and the OpenTelemetry endpoint (also not checked before). Errors never repeat the URL. If you ran 0.5.5 or earlier with a token in a URL and INFO logging on, treat the token as exposed and rotate it.
    • A failure's own text no longer leaves the local log. When a worker failed, the supervisor put the exception's text into the synthesis prompt it sent to a model, and failure events and audit records stored it too. That text is whatever raised it: in 0.5.4 and earlier it could be a provider's reflected API key, and in any version it can be an upstream message, a URL or a value from a request. Events also reach a collector through the OpenTelemetry exporter. Synthesis prompts, the run.finish and worker.failed audit records, and the model.call.failed, worker.failed and run.finished events now carry only the exception type and a fixed description, such as RuntimeError: worker failed. The full text, with its traceback, is written to the local forge.failures log at WARNING.

    Added¶

    • default_query on OpenAIProvider and OpenAICompatibleProvider, and openai_compatible_default_query (FORGE_OPENAI_COMPATIBLE_DEFAULT_QUERY, form-encoded) in the configuration, for parameters an endpoint requires on every request, such as an api-version. The values are sent but kept out of records and logs: SecretStr in the configuration, absent from provider descriptions, events and errors, and redacted from the log lines of the HTTP client and the vendor SDKs. No shipped preset needs one.

    Changed¶

    • OllamaProvider refuses credentials in its URL instead of moving them into a Basic auth header, as 0.5.5 did. One rule now covers every configured URL. Migration: remove user:password@ from OLLAMA_BASE_URL; if your Ollama sits behind an authenticating proxy, configure the proxy rather than the URL.
    • The error field of those events and audit records is now "<ExceptionType>: <fixed description>", and a new error_type field holds the type alone. Code that read the exception's message from them should read the local forge.failures log instead.

    [0.5.5] - 2026-11-24¶

    Security release, with the OpenAI-compatible provider work. Upgrade if you use any network provider through a proxy, gateway or endpoint you do not control: see Security. Imports, public API and CLI commands are unchanged. Two behaviours changed on purpose and are called out first under Changed: Bedrock is no longer wired automatically from an instance profile, and provider error messages no longer include upstream text.

    Added¶

    • OpenAICompatibleProvider (forge.models.providers.openai_compatible, registry key openai_compatible): one generic provider for any endpoint that speaks the Chat Completions API, configured by a named preset, a base_url, or both. Vendor names appear only in the preset data, never in a module, class or CLI name.
    • Provider presets as a versioned data file, provider-presets.v1, with a JSON Schema. Each preset records a base_url, a documentation link, the vendor's stated jurisdiction, and whether the endpoint is local or hosted. A preset is data, not a claim: no vendor API was contacted by this project, and the tests run against a fake in-process server only.
    • Configuration fields openai_compatible_base_url, openai_compatible_preset and openai_compatible_api_key_env (environment: FORGE_OPENAI_COMPATIBLE_BASE_URL, FORGE_OPENAI_COMPATIBLE_PRESET, FORGE_OPENAI_COMPATIBLE_API_KEY_ENV). The last names the environment variable that holds the key; the key itself is never stored in configuration. With none of these set, nothing changes: the openai provider is built exactly as before.

    • Every model.call.started event now carries hosting, jurisdiction and provider_preset beside provider, for every provider. Where nothing is known the value is the literal "unknown", never an omission. Hosting for a custom base_url is derived from the endpoint, and its jurisdiction is "unknown". RunContext.policy_request_block(model) returns the same facts in the model / provider shape a policy engine matches on.

    • User-supplied preset files. provider_presets_path (FORGE_PROVIDER_PRESETS_PATH) names a provider-presets.v1 file of your own, loaded alongside the built-in presets and validated the same way. A jurisdiction declared there is reported as attested, like the shipped ones. An id that collides with a built-in preset is an error, never a silent override.

    • model.call.started events also carry jurisdiction_verification (attested, unknown or not_applicable) and provider_preset_source (built_in or user).
    • docs/provider-coverage.md lists each preset's status. Ten of the eleven presets had their base_url read on the vendor's documentation on 2026-11-24 and are marked reviewed with that date; one is left unreviewed. A review reads documentation only. No vendor API was contacted. The review corrected one preset's host and three documentation links, and marked one more preset partial.

    Security¶

    • OpenAIProvider and OpenAICompatibleProvider refuse a base_url that contains credentials. Affects 0.5.4 and earlier. A URL such as https://user:password@host/v1 was accepted and used, and the HTTP client logs the request URL at INFO on every call, so the password reached the logs. Such a URL now raises ConfigurationError at construction, for base_url, for a preset's URL and for the SDK's own OPENAI_BASE_URL. The error names the scheme and host only. Remove the credentials from the URL and supply the key through api_key or its environment variable. If you ran 0.5.4 or earlier with credentials in a base_url and INFO logging on, treat them as exposed and rotate them.
    • OpenAIProvider error messages could contain the API key. Affects 0.5.4 and earlier. A failed request raised ProviderResponseError with the upstream error text interpolated into its message, and all three provider errors kept the SDK exception as their cause. Affects 0.5.4 and earlier. The same fault as the OpenAIProvider one above, in the other three providers that call out: - AnthropicProvider interpolated the upstream error into ProviderResponseError, and all three of its errors kept the SDK exception as their cause. A server or proxy that reflects request headers could put the x-api-key value into the message or the traceback. - BedrockProvider interpolated the botocore ClientError, which carries the service's message, and kept it as the cause on every error path including stream(). - OllamaProvider repeated the response body of any non-200 answer and the text of any transport error, which includes the request URL, and reported its configured base_url verbatim in the error context.     Fixed¶

    • Constructing an Orchestrator no longer attempts a network call. With boto3 installed, building the default providers asked boto3 to resolve AWS credentials, which walks the whole provider chain and ends at the instance-metadata address. Merely creating an orchestrator on a machine with no AWS configuration therefore tried to open a connection. Bedrock availability is now decided from local signals only: credential environment variables, a named profile, web-identity or container-credential variables, or the existence of a shared credentials file.

    Changed¶

    • Bedrock is no longer wired automatically from an instance profile. Migration: set FORGE_BEDROCK_ENABLED=1 (or bedrock_enabled = true). Before this release, building an Orchestrator asked boto3 to resolve AWS credentials, which ends at a network call to the instance-metadata service. That call is gone (see Fixed), so a host whose only AWS credentials come from an instance profile, such as an EC2 instance, ECS task or EKS pod role, no longer gets the Bedrock provider unless you ask for it. Hosts with credentials in environment variables or ~/.aws files are detected as before and need no change. With the setting on, boto3 contacts the instance-metadata service when the provider is built, which is the lookup the setting asks for.
    • Error messages from AnthropicProvider, BedrockProvider and OllamaProvider no longer include the upstream explanation (see Security). Code that matched on that text should read error.context instead: status_code, error_type, and code for Bedrock. Ollama's 400 and 404 errors carry a fixed hint in place of the server's wording, and the base_url in its error context is now the scheme, host and port only.
    • OpenAIProvider no longer decides between max_tokens and max_completion_tokens with a rule buried in the request path. The choice is now explicit data: a new token_param argument names the parameter to send for every model, and completion_token_model_prefixes (default ("o",)) drives the per-model choice when token_param is unset. Default behaviour against OpenAI's own API is unchanged, and a test compares every default outcome with the previous rule. The reason for the change is other endpoints: reached through base_url, a model whose name merely starts with "o" was sent max_completion_tokens, which its server may reject. Callers that know their endpoint can now say which parameter it takes.

    [0.5.4] - 2026-08-12¶

    Beta-hardening release. No new product features; imports, public API and CLI commands are unchanged. One intentional behavior tightening is called out under Changed below.

    Security & governance¶

    • ToolSandbox now enforces tool RBAC against the run principal: normal tools require USE_TOOL and dangerous tools require USE_DANGEROUS_TOOL.
    • Dangerous tools require both the USE_DANGEROUS_TOOL permission and explicit allowlisting before they may run.

    Budget reliability¶

    • Added concurrent pre-call budget reservations (conservative input + maximum output) held under a lock, reducing the risk of parallel workers collectively oversubscribing a hard cap. Reservations settle against provider-reported usage on success and are released on failure — no permanent reservation leak and no double-counting. Costs remain local list-price estimates, not invoices.

    Audit reliability¶

    • Redact actor and run identifiers (in addition to resource values) before writing audit records.
    • Serialize in-process audit writes per audit file; verify() fails closed on malformed/unparseable records. Multi-process audit-file coordination remains a known limitation. Hash chains are tamper-evident, not immutable.

    Configuration¶

    • Stricter validation: reject unknown configuration fields, malformed boolean environment values, non-positive tool timeouts, and invalid assignment.

    CLI¶

    • Added forge --version / forge -V. The existing forge version command is unchanged.

    Packaging¶

    • Declare supported Python as >=3.11,<3.14.
    • Pin the PyPI Trusted Publishing action to pypa/gh-action-pypi-publish v1.14.2 (Twine 7 / Core Metadata 2.5 compatible).

    Changed¶

    • Ollama is no longer auto-detected. Zero-configuration runs stay deterministic and offline (Echo). To enable the Ollama provider, set OLLAMA_BASE_URL explicitly (for a local or remote server).
